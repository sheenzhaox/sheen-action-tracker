## ADR-001 姿态推理在浏览器端运行（MediaPipe Tasks Vision）

**背景**：Workers Free CPU 10 ms / 请求；Workers AI 没有姿态模型；Containers 需付费。网页应用是主要形态。

**决策**：使用 `@mediapipe/tasks-vision` Pose Landmarker 在浏览器 Web Worker 中推理，通过 `PoseProvider` 接口隔离。

**备选方案**：
- 服务端 MMPose / RTMPose（GPU）：精度与模型选择更好，但需要付费计算和视频上传。
- 浏览器端 RTMPose（ONNX Runtime Web）：可行，作为 P5 的第二提供者。
- Sports2D：适合离线 Python 分析，不适合嵌入网页；作为精度对比基准。

**后果**：零服务端计算成本、隐私好；性能受用户设备限制；需要处理浏览器解码兼容性。

## ADR-002 视频本地优先，默认不上传

**背景**：样例 7.7 s 视频 51 MB；运动视频可能涉及未成年人；免费 R2 为 10 GB。

**决策**：视频只在浏览器处理；云端只同步姿态文件、manifest、指标和报告。视频上传是 P5 的可选功能，需要用户明确同意。

v0.3 补充（2026-10-29，GPT 评审 + 用户确认 Q10）：
- **离线边界**：v1 只承诺"页面和模型已加载后，断网也能完成分析"；冷启动离线（Service Worker 预缓存应用与模型）推迟到 P4。
- **跨设备**：已同步的分析在其他设备上只能看骨架、指标和曲线，状态为"源视频不在本设备"；重新选择同一视频（按哈希匹配）后才可叠加回放。v1 不专门做跨设备体验。
- **云端不存图片**：关键帧截图会暴露人脸和环境，只在本地从视频生成；云端报告只有数值和曲线。

**后果**：隐私和成本优势明显；换设备时无法回放原视频叠加骨架（可以只回放骨架动画）。用户确认（Q6，2026-10-29）：原视频暂时只保存在本地。

## ADR-003 单个 Worker 托管前端与 API

**背景**：Cloudflare 推荐新项目使用 Workers + Static Assets；项目规模小。

**决策**：一个 Worker 同时服务 SPA 静态资源和 `/api/*`、`/models/*`，使用 `@cloudflare/vite-plugin` 开发。

**备选方案**：Pages + 独立 API Worker（多一个部署单元，无明显收益）。

**后果**：部署与鉴权简单，同源无 CORS；需要注意 API 代码保持轻量。

## ADR-004 Pose Track（PTRK）+ manifest 为核心持久化资产

**背景**：分析算法会持续迭代；重新推理需要原视频和较长时间。

**决策**：保存原始与处理后的姿态轨迹（PTRK 二进制 + gzip），以及记录全部输入与参数的 manifest（`recipeHash`，见 02 第 11 节）。

v0.3 修订（2026-10-29）：**"可重算"只在以下范围内成立**，不再笼统承诺"分析结果可从 PTRK 重新计算"：

| 改变的内容 | 需要的输入 |
|---|---|
| 分析规则、分段参数、指标定义 | 处理后 PTRK + manifest |
| 后处理参数（插补、重采样、滤波） | 原始 PTRK + manifest |
| 模型、目标人物、推理分辨率、帧率 / 时间映射 | **原视频**（重新推理） |

**后果**：算法升级可以在上述范围内重算历史数据；需要维护 PTRK 格式版本兼容（v1 在第一个 P1 分析包完成前不算冻结）。

## ADR-005 运动以可插拔分析包实现，分析代码为纯 TypeScript

**背景**：网球与健身差异大，未来还可能加入更多运动或动作。

**决策**：定义 `AnalysisPack` 接口；每个包是独立 workspace package；`analyze()` 为确定性纯函数（包括事件 ID），参数以 JSON 配置并写入 manifest。

**后果**：可以在 Node 中用 fixtures 做回归测试；新增动作不改核心管线；需要维护通用特征库的稳定 API。

## ADR-006 D1 存元数据与指标，R2 存二进制对象

**背景**：需要按运动员、指标、时间查询趋势；姿态文件为二进制且可能超过 D1 单行 2 MB 上限。

**决策**：D1 使用长表 `metrics(metric_key, value)` 支持趋势查询；PTRK 与报告存 R2，D1 只存 key。

**后果**：查询灵活、新增指标无需迁移；跨 D1 和 R2 的删除需要应用层保证一致性。

## ADR-007 v1 使用 Cloudflare Access 做身份验证（按路径保护）

**背景**：v1 使用者为本人 + 少量教练试用（Q3，2026-10-29 确认），不需要公开注册；公开发布在 v2 或以后。同时架构要求"没有账号也能在本地完整使用"（ADR-002）。

**决策**（2026-10-29 评审修订）：
- Access **只保护 `/api/*`**（`/api/health` 除外）；SPA 静态资源和 `/models/*` 公开。
- 登录通过**顶层导航**到 `/api/auth/login` 完成（fetch 遇到 Access 跳转会因 CORS 失败）。
- Worker 自行校验 Access JWT：RS256 签名（缓存 JWKS，未知 `kid` 时刷新）、`iss`、`aud`、`exp`。
- 用户以 JWT 的 `iss + sub` 映射，邮箱只作可变属性。

**备选方案**：
- 用 Access 保护整个应用（初版方案）：与匿名本地使用冲突，未登录用户连页面都打不开，已放弃。
- 自建账号（邮箱魔法链接 / OAuth）：公开发布时再实现。

**后果**：零账号系统开发量，匿名本地使用不受影响；用户数受 Zero Trust 免费计划限制；使用 workers.dev 时以"主机名 + `/api` 路径"的 self-hosted 应用实现，**不得启用 Worker 级 Access**（会锁住整个站点），部署时实测按路径保护是否生效；公开产品前需要迁移鉴权方案。

## ADR-008 HEVC/HDR：运行时探测 + 拍摄指引，不做服务端转码

**背景**：iPhone 默认 HEVC 10-bit HDR（样例即是），非 Safari 浏览器支持不稳定；服务端转码需要付费计算并上传视频。

**决策**：运行时探测解码能力；不可解码时给出明确指引（Safari、相机"兼容性最佳"、关闭 HDR、导出 H.264）。P1 spike 评估本地转码（ffmpeg.wasm）的可行性。

**后果**：部分用户首次使用会遇到阻碍；保持零服务端成本与隐私承诺。

## ADR-009 模型自托管，heavy 模型放 R2

**背景**：静态资源单文件上限 25 MiB；heavy 模型 29.2 MB；运行时依赖第三方 CDN 存在可用性与版本漂移风险。

**决策**：lite / full 模型和 WASM 作为静态资源；heavy 模型放 R2，经 `/models/*` 提供并长期缓存。路径中包含版本号。

**后果**：版本可控；发布流程需要包含模型同步步骤。

## ADR-010 手机浏览器为一等目标平台，同一代码库按能力降级

**背景**：视频主要由手机拍摄；iPhone Safari 原生支持 HEVC / HDR；WebCodecs（iOS 16.4+、Android Chrome 94+）、Worker 内 WebGL2（iOS 17+）、OPFS 在主流手机浏览器均可用。

**决策**：不开发原生 App。桌面与手机共用同一 Web 代码库，通过能力探测与设备基准测试选择解码路径、模型档位和推理分辨率。**iPhone（iOS 17+ Safari，推荐 18.4+）为主平台和验收平台**（2026-10-29 用户确认）；桌面浏览器次之；Android Chrome 尽力支持，不作为验收条件。

**备选方案**：原生 App（iOS / Android MediaPipe SDK）——性能和后台处理更好，但开发和发布成本高；如果移动端 spike 不达标再评估。

**后果**：需要处理内存上限、后台挂起、发热降频、相册导出转码等问题（见 [07-mobile-web.md](./07-mobile-web.md)）；不支持 Firefox Android 的 WebCodecs 路径，使用 `<video>` 回退路径。

## ADR-011 时间模型与指标质量契约

**背景**（GPT 评审 G01/G02/G03）：iPhone 慢动作文件的播放时间不等于真实时间；插补和重采样会让曲线"看起来"帧率更高；`visibility` 不是测量精度。v0.2 用 `minFps` 判断可用性，无法发现这些问题。

**决策**：
- 区分播放时间 `tPlay`、真实时间 `tReal` 和处理采样率；`timeMap` 记录来源与是否可信。慢动作或不确定时 `trusted = false`，所有依赖真实时间的指标（速度、节奏）为 `unavailable`。
- 指标可用性按**原始观测**判定（关键窗口最大观测间隔、观测比例），插补和重采样**不能提高可用性**；关键极值依赖插补点时指标不可用。
- 每个关键点带 `kpState`（observed / interpolated / missing / rejected），每个指标带 `status`（valid / unavailable / experimental）、原因和测量空间。
- 依赖竖直方向的指标需要竖直参考（用户确认相机水平或手工画线），不从骨架自动估计横滚角。
- 后处理在完整轨迹上一次完成，在人物切换、推理分段边界、时间不可信处断开。

**备选方案**：保留 `minFps` + 置信度降低（v0.2）——实现简单，但会把不可测的值当作可测的值展示。

**后果**：报告中会出现较多"不可用"及原因，需要 UI 清楚解释；拍摄指引（关闭 HDR、普通 60 fps、三脚架水平）变得更重要；测试需要覆盖慢放、插值、漏帧等反例。详见 [02-pose-pipeline.md](./02-pose-pipeline.md) 第 3、7 节和 [03-analysis-packs.md](./03-analysis-packs.md) 第 6 节。

## ADR-012 v1 只做测量，不做动作纠错

**背景**（GPT 评审 G04，用户确认 Q8）：v0.2 的规则示例（如"膝屈曲 < 90° 为偏浅"、"脚跟抬起为警告"）没有经过验证，也不适用于所有人和所有训练目的；单目 2D 测量误差尚未量化。

**决策**：v1 只输出描述性测量（次数、角度、节奏、骨架回放）和测量说明（为什么某个指标不可用）。`Finding` 保留 `category`，v1 只产生 `measurement` 类，`severity` 只用 `info`。不提供默认纠错阈值，不使用受伤风险表述。

**后续**：纠错类提示只在用户 / 教练自设目标、规则注明适用条件与依据、相关指标为 `valid` 时启用（"目标模式"）；Workers AI 文字总结（P5）同样受此约束。

**后果**：v1 价值集中在可信的测量和趋势；避免给出错误建议；用户需要自己解读数值。

## ADR-013 UI 设计系统：测量工具风格，状态不只靠颜色

**背景**：用户要求按 [ui-ux-pro-max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill)（v2.15.0）技能做 UI/UX 设计。技能生成的方案（产品类型 Fitness/Gym App）有几处不适合本项目：绿色主按钮配白字（对比度 2.28:1）、卡片与背景同色、营销落地页结构、GSAP 滚动动效、建议加入游戏化。

**决策**：以核对后的 [MASTER.md](./design-system/action-tracker/MASTER.md) 为唯一设计 token 来源，页面规格见 [08-ui-ux.md](./08-ui-ux.md)。要点：
- 深色为默认，浅色用于户外强光，跟随系统；视频舞台两种主题都是黑底。
- 主色橙 `#F97316`（浅色 `#EA580C`），主按钮用**深色文字**；绿色只表示 `valid`。
- 指标状态一律**图标 + 文字**；`unavailable` 显示"—"和原因，不显示数值。
- 骨架线条下加深色描边，保证在各种球场背景上可见；`kpState` 用实心/空心、实线/虚线区分。
- 不做游戏化、评分、等级；事件称"速度峰值"，不称"击球"。
- 只用 CSS 过渡；字体自托管，不在运行时请求外部资源。

**备选方案**：直接采用技能生成结果（对比度不达标、语义冲突）；使用通用组件库默认主题（缺少骨架叠加和指标状态规范）。

**后果**：实现前每个页面需对照 MASTER 第 10 节检查清单；新增颜色须计算对比度后写入 MASTER；技能的后续输出只作参考，必须核对后才能写入。

## ADR-014 UI 采用方案 C + shadcn/ui + Tailwind CSS v4

**背景**：2026-10-29 用户从三个 shadcn 风格原型中选定 C（Mobile focus：全宽画面 + 可拖动底部抽屉，骨架画在真实身体上），2026-10-30 确认实际应用采用 shadcn/ui + Tailwind。ADR-013 把是否采用工具类框架留到 P1 脚手架时决定。

**决策**：
- 布局以 [mock-ui-shadcn-c.html](./mockups/mock-ui-shadcn-c.html) 为准；A / B 只作参考。
- 组件用 shadcn/ui（源码复制进 `apps/web/src/components/ui/`，基于 Radix 原语），样式用 Tailwind CSS v4（`@tailwindcss/vite`，`@theme inline` 映射变量）。
- token 改用 shadcn 变量名（`--background`、`--primary`、`--input` 等），取值以 C 的 zinc 中性色为准，每个值的对比度写在 [MASTER](./design-system/action-tracker/MASTER.md) v0.2 第 3 节；项目专有变量（`--valid`、`--experimental`、`--warning`、`--primary-text`、`--stage`、骨架色）同样写入 MASTER。
- 字体改为系统字体（iPhone 上即 SF Pro），不再自托管 Barlow；图标仍用 Phosphor，替换 shadcn 默认的 lucide。
- 本 ADR 补充 ADR-013，不取代它：除"字体自托管"一项改为系统字体外，ADR-013 的状态表达、主按钮深色字、骨架描边、无游戏化等规则全部继续有效。

**备选方案**：纯 CSS 变量 + 手写组件（工作量大，可访问性需自己实现）；MUI / Chakra 等运行时组件库（主题定制重，包体大，与 C 的风格不符）。

**后果**：
- 构建依赖增加 Tailwind 与 Radix，但没有运行时外部请求。
- shadcn 组件代码归本仓库所有，升级需手工合并。
- 加入新组件后要检查触控目标 ≥ 44 px、图标为 Phosphor、颜色只用 MASTER 变量。

## ADR-015 网球持拍手与反手类型属于运动员档案，不设全局默认

**背景**：Q12 回答（2026-10-30）：
- 首个网球包先做正手 + 反手（`tennis.groundstroke`），发球放 P2。
- 不同球员的持拍手不同。
- 反手大多是双手。
- 网球测试视频近期没有，P1 先只用 sample1。

**决策**：
- `dominantHand`（`right` / `left` / `unknown`）与 `backhandType`（`two_handed` / `one_handed` / `unknown`）是 **Athlete** 档案字段。
  - 新建档案时持拍手必填，可选 "Unknown"；反手类型预选 `two_handed`。
  - 每次分析把两者写入 manifest 的档案快照（ADR-004），分析页可临时改并只影响本次快照。
- 持拍手为 `unknown` 时按 03 第 5.2 节取手腕速度峰值更大的一侧，并在报告中注明"持拍手为推断"；正 / 反手分类置信度降低，低于阈值标 `unknown`。
- `backhandType` 只用于分类辅助（双手反手看两手腕距离），不改变任何指标的定义。
- 网球分析包实现可在 P1 用合成 / 手写 PTRK 做单元测试；**召回率等验收指标要等真实网球视频与标注**，在此之前网球包状态为 experimental。

**备选方案**：全局设置"我是右手"（不适合教练给多名学员分析）；完全自动推断（左手球员与反手容易混淆）。

**后果**：Athlete 档案在 P1 就需要（本地 IndexedDB）；fixtures 需同时覆盖左右手；P1 首个里程碑仍以 sample1 打通管线与关节显示为准。

## ADR-016 应用采用 SpaceX-inspired 黑白排版视觉方向

**背景**：用户提供 `DESIGN-spacex.md` 并确认将其视觉方向用于 Action Tracker。原型确认了纯黑画布、大写工程感标题、hairline 分隔和桌面顶栏导航，同时应用仍需适配手机视频分析工作流。

**决策**：
- 深色主题采用纯黑背景、近黑表面、白色 display 字体和灰色装饰分隔线；标题、导航与小标签使用全大写。display 优先系统已有的 Arial Narrow / Aptos Narrow，不下载 D-DIN。
- 桌面使用顶栏与横向页面导航；手机保留固定底部三标签导航和安全区间距。
- 保留浅色主题、shadcn/ui + Tailwind（ADR-014）、橙色主按钮 + 深色文字、指标状态图标 + 文字、测量工具语义及本地隐私规则（ADR-013）。
- Records feature 只用真实保存的帧数和元数据，不自动显示视频缩略图；视频只在用户选择并通过校验后用于回放。

**备选方案**：原样采用 SpaceX 营销页面（全屏英雄视频、无工具导航、纯白 ghost CTA）——不适合重复使用的分析工具，且会违反主按钮与本地视频规则；维持原 zinc 卡片外观——与用户确认的视觉方向不符。

**后果**：深色主题层级更克制，桌面记录页获得更宽的内容空间；浅色主题和已有测量流程不变。新色值、字体与页面规格见 [MASTER v0.3](./design-system/action-tracker/MASTER.md) 和 [08 第 5、11.3 节](./08-ui-ux.md)。
