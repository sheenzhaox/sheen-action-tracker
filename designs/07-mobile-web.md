# 07 · 移动端浏览器方案

> 状态：v0.3 草案 · 更新：2026-10-29（GPT 评审修订：30 s 片段、同页恢复、慢动作只用于计数） · 浏览器支持数据来源：MDN browser-compat-data（2026-10-29 查询）

## 1. 结论

**可以在手机浏览器上实现**，且手机是一等目标平台：

- 拍摄设备就是手机，"拍完即分析"体验最好。
- **iPhone Safari 原生支持 HEVC / HDR**，样例视频这类 iPhone 默认格式在 iPhone 上反而是兼容性最好的环境。
- 所需 Web API 在 iOS 17+ 与较新的 Android Chrome 上都已具备。

但**能否流畅运行取决于具体机型**，必须用 P1 spike 实测（见第 6 节）。手机端与桌面端使用同一套代码，只做能力探测与参数降级，不另做原生 App。

### 1.1 平台优先级（2026-10-29 用户确认）

| 优先级 | 平台 | 定位 |
|---|---|---|
| **主** | **iPhone（iOS 17+，推荐 18.4+）** | 拍摄 + 分析 + 查看报告的主要设备；所有功能必须在此验收 |
| 次 | 桌面 Chrome / Edge / Safari | 大屏查看、回看历史与趋势；iPhone HEVC 视频在 Windows 上可能无法解码，需走提示或回退 |
| 尽力支持 | Android Chrome | 保持代码兼容，不作为 P1 验收条件 |

**iPhone 上所有浏览器都是 WebKit 内核**：Chrome、Edge、微信内置浏览器等在 iPhone 上与 Safari 共用同一引擎（欧盟地区允许其他引擎，属例外）。所以 iPhone 的兼容性主要看 **iOS 版本**，不看浏览器品牌；但 App 内置浏览器仍可能限制文件访问和 Wake Lock，需检测并提示"在 Safari 中打开"。

推荐 iOS 18.4+ 的原因：Screen Wake Lock 从 18.4 起才完整支持，长时间分析时防止锁屏。iOS 17.0–18.3 也能分析，但需提示用户手动保持屏幕常亮。

## 2. 关键 API 支持情况

| 能力 | 用途 | iOS Safari | Android Chrome | Firefox Android |
|---|---|---|---|---|
| WebCodecs `VideoDecoder` | 解码路径 A | 16.4+ | 94+ | ❌ → 回退路径 B |
| OffscreenCanvas `webgl2` | Web Worker 中 MediaPipe GPU delegate | **17+** | ✅ | 需实测 |
| OPFS `storage.getDirectory()` | 本地保存姿态文件 | 15.2+ | 109+ | 111+ |
| Screen Wake Lock | 长时间分析时防止锁屏 | **18.4+**（16.4–18.3 部分支持，主屏幕 Web App 中无效） | 84+ | 126+ |
| `getUserMedia` | 实时摄像头模式（未来功能，Q5） | ✅（需 HTTPS） | ✅（需 HTTPS） | ✅ |
| HEVC 10-bit HDR 解码 | iPhone 默认格式 | ✅ 原生 | 取决于芯片，需探测 | 需探测 |

**最低支持基线（建议）**：iOS / iPadOS 17+ Safari；Android Chrome 最近两个大版本。低于基线时降级为 CPU 推理或提示升级。

> 以上为 API 是否存在；MediaPipe 官方仅说明支持 "Chrome or Safari"，未单独承诺移动端性能，需实测。

## 3. 手机端特有风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **内存上限** | 移动 Safari 单标签页内存有限，4K HEVC 帧很大，超限会直接刷新页面 | 解码队列 ≤ 2–3 帧；立即缩放到长边 960 并 `close()` 原帧；默认不保留帧缓存 |
| **切到后台 / 锁屏即暂停** | iOS 会挂起后台页面的 JS 与 GPU | 分析中申请 Wake Lock；提示用户保持前台。v1 只保证**同一页面内**暂停后继续（从上一个关键帧重新解码，约 1 s 重叠）；页面被系统刷新则重新分析（见 02 第 12 节）。30 s 片段重新分析代价可接受 |
| **发热降频** | 持续 GPU 推理数十秒后性能下降 | 默认 `lite` / `full` 模型（不用 `heavy`）；默认全部帧，Gym 只在性能不足时降到 30 fps（P2 先对比全帧与降帧结果；网球不降帧）；显示剩余时间；超过 30 s 时先让用户裁剪 |
| **从相册选视频可能被转码** | iOS 通过文件选择器提供视频时，可能压缩或转换编码，改变分辨率 / fps | Probe 阶段读取实际编码、分辨率、fps 并显示；与预期不符时提示改从"文件"App 选择 |
| **慢动作视频（120/240 fps）** | 导出的文件可能是已变速的版本，播放时间不再是真实时间 | 按 02 第 3 节时间模型检测（fps ≥ 100、编辑列表变速、iOS 慢动作标记）；检测到时 `timeMap.trusted = false`，**只用于计数和骨架回放**，速度与节奏指标不可用；拍摄指引改用普通 60 fps |
| **App 内置浏览器**（微信等） | 内核与系统浏览器不同，WebCodecs / WebGL2 / 文件访问可能受限 | 检测内置浏览器 UA，提示"在 Safari / Chrome 中打开" |
| **屏幕小** | 骨架回放、曲线、事件表难以同时显示 | 移动端单列布局：视频 + 骨架为主，曲线与事件用底部抽屉 / 标签页 |
| **实时模式无法看屏幕** | 运动中看不到手机 | 实时模式（未来功能）再用语音播报（`speechSynthesis`）与提示音做计数和提醒 |

## 4. 移动端默认参数

| 参数 | 桌面默认 | 手机默认 |
|---|---|---|
| 推理长边 | 1280 | 960（低端机 720） |
| 模型 | `full`（网球可选 `heavy`） | `lite` 或 `full`（由首次基准测试决定），不提供 `heavy` |
| Gym 采样 | 全部帧 | 全部帧（性能不足时降到 30 fps，见 02 第 4 节） |
| Tennis 采样 | 全部帧 | 全部帧，建议裁剪到击球片段 |
| 单次视频建议时长 | ≤ 30 s（典型，Q9） | ≤ 30 s（更长时提示裁剪） |
| 解码队列 | 4–8 帧 | 2–3 帧 |

模型档位由"设备基准测试"（首次运行处理 20 帧）选择并保存在本地；20 帧只用于选档位，持续性能以 30 s 片段的实测为准（见 02 第 10 节）。

### 4.1 iPhone 拍摄建议（写入应用内拍摄指引）

| 设置（iOS「设置 → 相机」） | Gym | Tennis | 原因 |
|---|---|---|---|
| 录制视频 | 1080p 30 fps 或 60 fps | 1080p 60 fps（机型支持时可用 120 fps **普通视频**；不要用慢动作模式，见 M7） | 4K 对分析无收益，只增加解码负担和内存压力 |
| 格式 | "高效"（HEVC）即可 | 同左 | iPhone Safari 原生解码；只有需要在 Windows 桌面分析时才改"兼容性最佳"（H.264） |
| HDR 视频 | 建议关闭 | 建议关闭 | 避免 HDR→SDR 色调映射影响推理（见 [02-pose-pipeline.md](./02-pose-pipeline.md) 第 2 节） |
| 运动模式 / 防抖 | 三脚架拍摄时可关闭"增强防抖" | 同左 | 防抖会裁切、轻微变形画面 |

## 5. 开发与测试注意

- WebCodecs、OPFS、`getUserMedia`、`crypto.subtle` 都需要**安全上下文**（HTTPS 或 `localhost`）。手机通过局域网 `http://192.168.x.x` 访问开发服务器时这些 API 不可用。
- 本地手机测试方案（都不需要部署）：
  1. Vite 开发服务器启用 HTTPS：用 mkcert 生成证书，把本地 CA 描述文件安装到 iPhone，并在「设置 → 通用 → 关于本机 → 证书信任设置」中开启完全信任（自签名证书在 iOS 上会被 Worker、WASM 加载等请求拒绝，不推荐）。
  2. **调试 iPhone Safari**：Safari Web Inspector 需要一台 Mac。开发机是 Windows 时：
     - 应用内置**诊断面板**（开发构建默认开启）：显示能力探测结果、解码/推理每帧耗时、内存估计、错误日志，并可导出为 JSON；
     - 可选接入页面内控制台（如 Eruda），只在开发构建中加载；
     - 有 Mac 时再用 Web Inspector 做深入调试。
  3. Android 用 `chrome://inspect` 远程调试（次要平台）。
- 如需临时公网 HTTPS 地址（如 Cloudflare Tunnel 快速隧道），会把本地服务暴露到公网，**需要用户批准**。

## 6. P1 移动端 Spike 验收项

**必须**在 iPhone（Safari，iOS 17+；样例来自 iPhone 16 Pro）上通过；Android Chrome 有设备时顺带记录，不作为通过条件。测试素材：`sample1.MOV`（4K60 HEVC HDR，单腿蹲，慢而清晰，用于骨架与关键关节显示）、按 4.1 节和 03 第 5 节拍摄规范拍的 **30 s 1080p60 SDR 网球视频**（首个分析包 `tennis.groundstroke` 的素材），以及一段 120 fps 慢动作视频：

| # | 验证项 | 通过标准 |
|---|---|---|
| M1 | 从相册 / 文件选择后，实际得到的编码、分辨率、fps、时长 | 记录差异；确认是否被转码 |
| M2 | WebCodecs 解码 HEVC 10-bit HDR 4K | 可解码，无崩溃 |
| M3 | Web Worker 中 MediaPipe GPU delegate 初始化 | 成功；失败时 CPU 回退可用 |
| M4 | lite / full 每帧推理耗时与各阶段耗时 | 记录 P50/P95；目标离线分析 ≤ 3× 视频时长 |
| M5 | 处理 30 s 1080p60 视频全过程的内存与发热 | 不刷新页面；记录降频情况 |
| M6a | 同一页面内切后台再回来（未被系统刷新） | **必须通过**：从暂停处继续，结果与不中断时等价（次数相同，关键时刻相差 ≤ 2 帧） |
| M6b | 长时间后台导致页面被系统刷新 | 只记录行为：发生频率、OPFS 临时目录是否被正确清理；v1 重新分析即可 |
| M7 | 慢动作视频的时间戳 | 能被识别为时间不可信；速度与节奏指标为 `unavailable`，计数和回放正常 |
| M8 | 同一 iPhone 上用 Chrome、微信内置浏览器打开 | Chrome 行为与 Safari 一致；内置浏览器能被识别并提示"在 Safari 中打开" |

结果记录到 [workflow.md](../workflow.md)，并据此修订第 4 节默认参数。
